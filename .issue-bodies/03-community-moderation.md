Covers `0015_community_moderation.sql` and the moderation UI pushed in the batch: moderators cannot decide, contributors cannot appeal, and report consolidation loses data.

## Checklist

- [ ] **[high]** `src/components/moderation/ModerationQueue.jsx:42` — `<CaseDetail>` is rendered without `isMod` (nor `onAppeal`/`appealing`), while `CaseDetail.jsx:114` gates the decision section on `{isMod && !isDecided}`. Trigger: sign in as `community_moderator` → `/moderation` → "Review" → reports render but **Keep / Remove / Escalate never appear**. The whole decision flow is dead in the UI (server RPCs are fine; only reachable via direct API). `ModerationQueue` is the only caller of `CaseDetail`.
- [ ] **[high]** Appeal is unreachable from every angle: (a) `src/pages/Moderation.jsx:22` shows non-moderators an "only moderators" message, so a contributor can never reach `CaseDetail`'s appeal section; (b) `getModerationQueue` filters `.is('decision', null)` and `.is('appeal_of', null)`, so decided originals and appeal rows never appear for anyone; (c) `Moderation.jsx` never passes `onAppeal`/`appealing`, so `useModeration.appealCase` and `moderation.fileAppeal`/`getAppeals` are dead code (no caller). Server side: the `moderation_cases` SELECT policy (`0015:349`) is moderator-only, so a contributor cannot even read their own case. Feature scenarios for appealing a removal are unreachable end to end.
- [ ] **[high]** `0015:187-206` — a successful appeal never reinstates the entry: the `remove` branch flipped `public_songs.status` to `'removed'`, but an appeal decided `'keep'` only closes reports and notifies. Nothing restores `'live'` (`0010` grants clients SELECT-only on `public_songs`), so the contributor's entry stays removed forever and the scenario "A successful appeal reinstates the entry … with its previous history" cannot happen.
- [ ] **[high]** `0015:164-166, 222-233` — `escalate` writes a non-null `decision`, after which every `decide_moderation_case` call raises `'Already decided.'`, and the queue filters `decision is null`. The feature says the case waits "**until the system admin decides**" — no SQL path exists for that decision. Compounding: `decide_moderation_case` requires `is_community_moderator` (`0015:152`), so a pure `system_admin` always gets `'Not a moderator.'`. Escalated cases dead-end.
- [ ] **[high]** `0015:249-268` — `file_appeal` only rejects appealing a row that *is* an appeal; it never checks whether an appeal for `p_case_id` already exists or was decided. Trigger: a rejected contributor appeals the original case again → unlimited fresh appeal rounds, violating "an unsuccessful appeal is final at the in-app level"; rapid repeats also create duplicate **open** appeal rows.
- [ ] **[medium]** `0015:95-105` — `reason_counts`/`grounds` are rebuilt from **pending** reports only after every insert (overwrite instead of accumulate). Reporter A files reason x → case `{x:1}`; A's report becomes `consolidated`; reporter B files reason y → recount sees only pending → case overwritten to `{y:1}`, `grounds=[y]`. Reporter counts never accumulate and earlier reasons vanish; a later report on reason x re-queues as a *new* case, breaking "decided grounds never re-queue".
- [ ] **[medium]** `0015:107-110` — if all pending reports match already-decided grounds, the aggregates are empty but an **open case with `grounds = '{}'`** is still inserted → phantom queue entry, violating "the report does not create a new moderation case".
- [ ] **[low]** `src/lib/moderation.js:57,197` — `'Invalid reason.'`, `'You must be signed in.'`, `'Invalid decision.'` are thrown **inside** `withErrorMapping`, whose `handleError` only re-throws messages in `USER_ERRORS` → they always surface as "Something went wrong." The validation diagnostics are decorative.
- [ ] **[low]** `src/components/moderation/ModerationQueue.jsx:38` — after a decision the queue refetch drops the case, `queue.find` returns `undefined`, `CaseDetail` unmounts and `setActionSuccess('Decision recorded…')` runs on an unmounted child → no confirmation is ever seen.
- [ ] **[low]** `src/hooks/useModeration.js:20` — `isModerator` effect has no cancellation/stale-user guard (repo pattern elsewhere uses one): on rapid identity change a slow response from the previous user can set `isMod` for the wrong identity. Data stays protected by RLS.
- [ ] **[low]** `0015:332-341, 353-376` — UPDATE policies exist on `reports`/`moderation_cases` but only SELECT/INSERT are granted → inoperative dead code (latent `WITH CHECK` gap: `reports_update_self_pending` doesn't pin `reporter_id`/`public_song_id` if a grant is ever added).
- [ ] **[low]** `0015:195-198` — appeal upheld with `'remove'` runs the remove branch again on the still-existing row → `confirmed_violations` increments twice for one violation.
