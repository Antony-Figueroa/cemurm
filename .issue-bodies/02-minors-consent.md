The minor/consent machinery from `0017_minors_guardian_consent.sql` + the frontend gates pushed in the Hito 4 batch. The server-side lock never engages, and where it does engage the wrong actor holds the key.

## Checklist

- [ ] **[critical]** `0017:51 + 131` vs `src/lib/auth.js:71` — nothing in the repo ever writes `profiles.date_of_birth` (grep over `src/` and `supabase/`: comments only; `handle_new_user` inserts `(id)` only), so `is_minor` stays at its `default false`, `private.session_is_minor()` is **always false**. Two failures:
  1. *Functional:* a minor signs up → lock screen → records guardian consent → RPC raises `Consent is only required for minors.` (`0017:284`). The account can **never** unlock.
  2. *Security:* the publish guard `if session_is_minor() and not exists (consent)` (`0017:227`) never fires → the server-side "guardian approval required" lock is completely off; only the client-side UI gate remains, and any direct call to `publish_song_to_library` bypasses it.
  The migration comments claim "the app routes on `user_metadata`", but the RPCs read the DB flag. The two worlds are never connected.
- [ ] **[high]** `0017:71` — `grant update (date_of_birth) on public.profiles to authenticated` + the recompute trigger (`0017:51`) let the minor's own session rewrite `date_of_birth` → `is_minor` flips to `false` → active consent is archived (`0017:53-57`) → publish guard and revocation scenario both bypassed in a single `PATCH profiles`.
- [ ] **[high]** `0017:318-337` + `src/pages/SongDetail.jsx:643` — "Approve public sharing" is rendered in the **minor's own** song page and the RPC requires `p_user_id = auth.uid()` **and** `session_is_minor()`, i.e. the only possible actor is the minor. Feature (`features/minors-and-guardian-consent.feature:34`) requires "**when the guardian approves**". As written the minor self-approves their own public sharing (the `window.confirm` copy "Your guardian can revoke this later" documents the gap). Compare with `revoke_guardian_consent` (`0017:354+`), which is deliberately login-less via `guardian_email + revocation_token` — approval has no equivalent capability path.
- [ ] **[medium]** `0017:160-163` — the minor exclusion is added to `profiles_select_search` with no org-scoped exception. Trigger: an instructor at an org opens a student minor's profile → the row is invisible (cannot even read name/username). The exclusion was specified for *public* surfaces; as written it deletes minors from org rosters too.
- [ ] **[medium]** `0017:44-66` — `is_minor` is recomputed only on `update of date_of_birth`, and no cron/recompute path exists (`grep pg_cron|schedule|recompute` → nothing). A minor who turns 18 keeps `is_minor = true` until someone re-saves a dob that nothing ever writes. The header claim "flipped OFF on the 18th birthday" is not what the DDL does.
- [ ] **[low]** `0017:51` — `current_date - interval '18 years'`: Feb-29 birthdays become adult on Feb-28 of a non-leap year, and `current_date` uses the DB timezone (UTC on Supabase), shifting the boundary with the session timezone. Trivial, fails closed.
- [ ] **[low]** `src/pages/SongDetail.jsx:260-272` — `consentStatus` starts `null` and the `.catch` keeps it `null`, so a transient consent fetch failure disables "Contribute to library" with "Guardian approval required for public sharing" and no retry until reload — even when the server would have allowed the publish.
- [ ] **[low]** `src/components/auth/AuthGuards.jsx:29` — `checking` starts `false`, so a consented minor reloading a protected route flashes the guardian-consent **form** before the effect runs. Fail-closed, but the wrong screen; the same silent `catch` leaves `consent = null` (locked, no error shown) on a transient failure.

## Notes

- Batch 1 (in progress): the critical + both highs. Fix direction for the critical: derive `is_minor` server-side at account creation from `auth.raw_user_meta_data` (insert-time only, so post-signup `updateUser` cannot flip it), and revoke the client write path to `date_of_birth`.
